# XRG-ng 0.2.3: one settings window, one settings model, Aether7b

Status: approved in conversation on 2026-11-06; this document is the written spec.

## Goal

Give macOS and Linux the same settings window, organised, labelled and styled
the same way, backed by one settings model and one settings file format, drawn
only with the Aether7b design language (`~/src/aether7b`, v1.1). Ship it as
0.2.3, together with the unmerged sensor-naming work and a Stocks graph on
Linux.

## Decisions

| # | Decision |
|---|---|
| D1 | Version 0.2.3, build 4. 0.3.0 stays reserved for the Windows port and full UX parity. |
| D2 | The sensor work lands first: the 45 sensor-identity research commits on `fix/ai-log-same-size-rewrites` and PR #6 (`sensors/community-sensor-names`), rebased onto `main` (0.2.2). |
| D3 | One settings **catalog** and one settings **document** format, shared by both platforms. |
| D4 | **One implementation** of the model, in the shared Swift core (`XRGSharedCore`). Linux reads, validates, migrates and writes settings only through its C ABI; Rust keeps a typed, read-only mirror of the canonical JSON. |
| D5 | Both platforms store the same document. macOS migrates `NSUserDefaults` into it once; Linux converts its version-40 file once. Old data is left in place for downgrade. |
| D6 | The settings window uses Aether7b only: tokens, type, spacing, radii, motion, status rules and the native mapping in §5 of its README. |
| D7 | One section list on both platforms: General, Appearance, Graphs, Sources, AI, Weather, Stocks, Themes & import. |
| D8 | Stocks comes to Linux for parity: a shared Yahoo chart parser in the core, a Rust fetcher, a Stocks graph module. |
| D9 | Changes apply and save instantly on both platforms. No draft, no Apply button. |
| D10 | GLM implements each task, Codex reviews each task and the whole branch, Claude coordinates. The user approves every merge and every publish step. |

## Non-goals

- Windows UI. The shared core must still build and pass its tests on Windows.
- Redesigning the graph windows, menus, inspectors or About box. Only the
  settings window adopts Aether7b in this release.
- Changing what any graph measures.
- Moving framework-owned state into the document: Sparkle's `SU*` keys and
  AppKit window frames stay in `NSUserDefaults`.

## 1. Settings catalog

`Shared/Settings/settings-catalog.json`, bundled into `XRGSharedCore` as a
resource, is the single source of truth for what a setting is. Neither window
hard-codes a section, label, range or default.

Each entry:

| Field | Meaning |
|---|---|
| `id` | Stable dotted key, also the document path, e.g. `general.window.opacity`. Never reused. |
| `section`, `group` | Sidebar section (D7) and the card it belongs to. Order in the file is display order. |
| `label`, `help` | User-facing text, plain language, sentence case. `help` is optional, one sentence. |
| `control` | `toggle`, `choice`, `segmented`, `integer`, `decimal`, `duration`, `color`, `path`, `text`, `source`, `action`. |
| `default` | Typed default. |
| `range` / `options` | Bounds and step for numbers and durations, options for choices. Labels for options live here too. |
| `platforms` | `["macos","linux"]`, or one of them. A setting not available on this platform is not shown. |
| `legacy` | Where the value lived before 0.2.3: the macOS defaults key and the Linux v40 JSON path, with any value conversion. Used only by migration. |
| `depends` | Optional: another `id` and value that must hold for this control to be enabled. |

`source` controls take their options at run time from the platform: sensors,
network interfaces, disks, GPUs. The catalog names the source kind; the
platform supplies the list. PR #6's grouping (Identified, Unidentified,
Suspected unused) is part of the `temperature` source kind.

`action` entries are buttons: Check for updates, Reset section, Import, Export.

The catalog must cover every user-facing setting either app has today. Phase 2
starts with an inventory of every macOS defaults key and every Linux v40 field,
and every one is either mapped to a catalog id or listed, with a reason, as
deliberately kept out (see Non-goals).

## 2. Settings document

A JSON file, UTF-8, LF, sorted keys, two-space indent:

```json
{
  "format": "xrg-ng-settings",
  "version": 1,
  "settings": { "general.window.opacity": 0.85, "...": "..." }
}
```

- **Paths:** macOS `~/Library/Application Support/XRG-ng/settings.json`;
  Linux `$XDG_CONFIG_HOME/xrg-ng/settings.json` (default `~/.config`).
- **Writes are atomic:** write a temporary file in the same directory, fsync,
  rename. Mode `0600` on Linux, matching today's settings file.
- **Unknown keys are preserved** across a load and save, so the other
  platform's settings, and settings from a newer version, survive.
- **Invalid values** fall back to the catalog default for that key only and
  are reported as diagnostics; the rest of the file still loads.
- **An unreadable or malformed file is never overwritten.** The app runs on
  defaults, reports the problem in the window, and writes nothing until the
  user changes a setting and confirms replacing the file.
- **Version bumps** go through an explicit migration function per version in
  the core. Version 1 is the first.
- Opening the app, opening the window or idling never rewrites the file.

## 3. Shared core API

New files in `Shared/Sources/XRGSharedCore/`:

- `XRGSettingsCatalog.swift`: loads and validates the catalog; looks up entries
  by id and by section; filters by platform.
- `XRGSettingsDocument.swift`: parse, validate, apply defaults, migrate,
  serialise; set one value with validation; reset a section.
- `XRGSettingsMigration.swift`: macOS defaults → document, Linux v40 →
  document, both driven by the catalog's `legacy` fields.
- `XRGStockChart.swift`: parses the Yahoo chart responses macOS already uses,
  moved out of `XRGCore/XRGStock.swift`. macOS switches to it.

C ABI additions in `Shared/include/xrg_shared.h` and
`Shared/Bridge/XRGCBridge.swift`, bumping `xrg_shared_abi_version`. All take
and return UTF-8 JSON through caller-provided buffers, like the existing METAR
functions:

- `xrg_settings_catalog`: the catalog for a platform.
- `xrg_settings_load`: bytes in → canonical document plus diagnostics out.
- `xrg_settings_set`: document + id + JSON value in → new document or an error.
- `xrg_settings_reset_section`.
- `xrg_settings_migrate_linux_v40`: v40 JSON in → document out.
- `xrg_stock_chart_parse`: response bytes in → quote and history out.

Rust (`xrg-linux/rust/src/settings/`) keeps a serde mirror of the document for
reading typed values, built only from what the core returns. Every write goes
through `xrg_settings_set`, and the bytes the core returns are the bytes
written. Rust's existing upgrade chain for versions 10–39 stays, so old files
reach version 40 before the core converts them.

## 4. Migration

- **macOS, first launch of 0.2.3** with no `settings.json`: read every mapped
  defaults key through the catalog's `legacy` field, convert, validate, write
  the document. Leave every defaults key untouched so 0.2.2 still runs. A key
  that fails conversion takes its default and is logged; launch never blocks.
- **Linux, first launch of 0.2.3** with no `settings.json`: run Rust's existing
  upgrade to version 40 in memory, pass the result to
  `xrg_settings_migrate_linux_v40`, write `settings.json`. Leave `settings.conf`
  untouched so 0.2.2 still runs.
- After migration the document is the only source of truth for every catalog
  setting. 0.2.3 never writes the old locations.

## 5. Settings window

Built from the catalog on both platforms (D7). Section list and grouping are
those in the catalog; the mockup approved on 2026-11-06 is the visual
reference (`.superpowers/brainstorm/*/content/settings-layout.html`, local).

- **Layout:** a sidebar of sections and a scrolling content pane of flat,
  opaque cards, one per `group`, each led by a `//` mono eyebrow.
- **macOS:** programmatic AppKit, no nib. A full-height sidebar in an
  `NSVisualEffectView`, tinted with `--a7b-surface-chrome`, under a full-size
  content view title bar. The legacy `Resources/Preferences.nib` and its
  pane TIFFs are removed. `MainMenu.nib` is not touched; its Preferences item
  opens the new window.
- **Linux:** egui with a custom style generated from the tokens. A 40 px
  headerbar, 12 px window corners, and the opaque `--a7b-surface-chrome-fallback`
  sidebar (egui has no backdrop blur).
- **Aether7b only:** colours, type scale, spacing, radii, borders, focus ring,
  status and motion come from generated tokens (§6). No other colour, font or
  radius appears in the settings window. Light and dark follow the OS. Reduced
  motion makes every transition instant.
- **Controls:** toggles, segmented controls, choice menus, number and duration
  fields with their unit and range shown, sliders where the catalog gives a
  step, colour wells, path pickers, source pickers, action buttons. Inputs use
  the strong 3:1 rim and the 2 px Carolina focus halo.
- **Validation:** an invalid entry is not saved; its control shows the danger
  rim, dot and a mono label with the reason. Nothing else turns red.
- **Instant apply (D9):** each valid change is saved and takes effect
  immediately. Each section has a Reset to defaults action with confirmation.
- **Accessibility:** every control has an accessible label from the catalog;
  full keyboard navigation; VoiceOver on macOS reads section, group and label.

## 6. Aether7b tokens

`Tools/aether7b-tokens.py` reads `aether7b.tokens.json` (a copy vendored at
`Shared/Design/aether7b.tokens.json`, with its version and source commit) and
generates `XRGCore/XRGAether7b.swift` and `xrg-linux/rust/src/ui/aether7b.rs`.
A test regenerates both and fails on any difference, so tokens cannot drift by
hand. Updating Aether7b means replacing the vendored file and regenerating.

## 7. Stocks on Linux

- Same data and behaviour as macOS: the same ticker list format and limits, a
  one-year daily history and a 15-minute intraday quote from the Yahoo chart
  API, the same refresh cadence and the same failure handling.
- The Rust fetcher reuses the HTTP client and timeouts already used for
  weather. Parsing goes through `xrg_stock_chart_parse`.
- A Stocks graph module on the Linux dashboard, off by default, matching the
  macOS graph's content.
- Stocks settings are ordinary shared catalog entries.

## 8. Phases

1. **Sensor work.** Rebase the research commits and PR #6 onto `main`, resolve
   overlaps with 0.2.2 (notably `XRGTemperatureState.swift`), review, CI,
   user-approved merge.
2. **Shared core.** Inventory, catalog, document, migration, Stocks parser,
   ABI, conformance corpus.
3. **Tokens.** Generator, generated files, drift test.
4. **macOS window.** Catalog-driven window, storage adapter, migration on
   launch, removal of `Preferences.nib`.
5. **Linux window and Stocks.** Catalog-driven egui window, ABI-backed storage,
   migration on launch, Stocks fetcher and graph.
6. **Release 0.2.3.** Version bump, upgrade baselines moved to 0.2.2 on both
   platforms, notes, gates, signed builds, publish.

## 9. Testing and acceptance

- **Conformance corpus** (`Shared/Tests/Fixtures/settings/`): valid, invalid,
  out-of-range, unknown-key, malformed and future-version documents, plus
  migration inputs from real macOS 0.2.2 defaults and Linux v40 files. The
  Swift tests check expected outputs; the Linux tests run the same files
  through the ABI and must get identical bytes.
- **Catalog coverage:** a test fails if any mapped legacy key has no catalog
  entry, or if any catalog entry has no control in either window.
- **Window tests:** each window, driven from the catalog, shows every entry for
  its platform with the right control, label, range and default; setting a
  value through the control changes the document; an invalid value is not
  saved.
- **Upgrade:** macOS seeds a disposable defaults domain with a 0.2.2 user's
  custom preferences, launches 0.2.3 and checks every value in the document.
  Linux CI upgrades a real 0.2.2 archive to 0.2.3 with custom preferences.
  Both also run 0.2.2 again afterwards and check it still reads its own,
  untouched settings.
- **Snapshots:** both windows, light and dark, are rendered to images for the
  user's visual review. They do not gate CI.
- **Stocks:** parser fixtures shared with macOS; the Linux module is tested
  against recorded responses, with no network in tests.
- **Gates:** `Tools/ci-macos.sh Release` on arm64 and x86_64, the Linux
  release gate in the ARM64 container, and CI on macOS, Windows and both Linux
  architectures, all green.
- **Release:** idle CPU on the signed macOS build stays within 1 percentage
  point of 0.2.2's measured 3.3% of one core with the same data.

## Risks

- **Catalog completeness.** Missing a key loses a user's setting on upgrade.
  The inventory and the coverage test exist for this.
- **Migration correctness on real data.** Mitigated by real-data fixtures and
  the upgrade checks on both platforms; old data stays for downgrade.
- **Linux now depends on the Swift core for settings.** Startup cannot proceed
  without it; the core is already required for history and accounting.
- **Sensor rebase.** The research line touches files 0.2.2 rewrote; it needs a
  careful merge and its own review before anything builds on it.
- **Yahoo's unofficial API** can change or rate-limit. Same exposure as macOS
  today; failures show as a status, never a crash.
