# XRG-ng 0.2.3 Unified Settings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One catalog-driven, Aether7b settings window and one shared settings document on macOS and Linux, plus Stocks on Linux, shipped as 0.2.3 after the sensor work lands.

**Architecture:** The shared Swift core owns the settings catalog, the `xrg-ng-settings` document, migration and the Yahoo chart parser. macOS uses them directly behind its existing `XRGSettings` API; Linux uses them through new C ABI functions and keeps its typed `Settings` struct as a "Linux view" the core produces. Both windows render from the catalog with generated Aether7b tokens.

**Tech Stack:** Swift 6.4 (XRGSharedCore SwiftPM package, XRGCore/AppKit), Rust 1.99.1 + egui 0.37, C ABI (`Shared/include/xrg_shared.h`), Python 3 tooling, Swift Testing, cargo test.

**Spec:** `docs/superpowers/specs/2026-11-06-xrg-ng-0.2.3-unified-settings-design.md`

## Global Constraints

- Version 0.2.3, build 4 (D1). Upgrade baselines move to 0.2.2 (`9a4b401063335417ba89fa22643eb430b10a0e8e`) on both platforms.
- The model has one implementation, in `XRGSharedCore` (D4). Rust never decides validity; it writes only the bytes the core returns.
- Document: `{"format":"xrg-ng-settings","version":1,"settings":{…}}`, UTF-8, LF, sorted keys, two-space indent, atomic write (temp file in the same directory, fsync, rename), mode `0600` on Linux.
- Paths: macOS `~/Library/Application Support/XRG-ng/settings.json`; Linux `$XDG_CONFIG_HOME/xrg-ng/settings.json` (default `~/.config`).
- Unknown keys are preserved; invalid values fall back per key with a diagnostic; a malformed file is never overwritten without the user's confirmation; nothing rewrites the file on launch, on opening the window or when idle.
- Old storage (macOS defaults, Linux `settings.conf`) is read once for migration and never written by 0.2.3.
- Sparkle `SU*` keys and AppKit window frames stay in `NSUserDefaults`.
- Changes apply and save instantly (D9). Section list and order: General, Appearance, Graphs, Sources, AI, Weather, Stocks, Themes & import (D7).
- The settings window uses only generated Aether7b tokens: no other colour, font, radius or motion value appears in settings-window code.
- `Resources/MainMenu.nib` is not modified.
- The shared core stays Foundation-only and keeps building and passing its tests on Linux and Windows (`windows.yml`).
- Existing gates stay green: `bash Tools/ci-macos.sh Release`, `bash Tools/ci-linux.sh release` (ARM64 container), `swift test` for the package, CI on all platforms.
- Standing rules: never `git stash`; never print the environment; no `sudo` on the Mac; never push, tag, merge or publish (the coordinator does, with the user's approval); scratch under `$TMPDIR/xrg-0.2.3-task-N/`, deleted at the end with an inventory of paths and sizes.

## Review Focus

1. A 0.2.2 Mac user with years of customised preferences upgrades: every visible setting must look and behave the same afterwards (pinned in Task 4 and Task 13).
2. A Linux user's settings file from any older version (10–40) upgrades without losing values (pinned in Task 10).
3. The user types an invalid value (out of range, empty, wrong unit): it is refused with a visible reason and nothing is saved, on both platforms (pinned in Task 9 and Task 11).
4. The settings file is malformed, read-only or on a full disk: the app starts on defaults, says so, and never destroys the file (pinned in Task 8 and Task 10).
5. Stocks with a bad ticker, no network or a changed Yahoo response: the graph shows a status, the app stays responsive and other graphs keep sampling (pinned in Task 12).
