# XRG-ng 0.2.2

A fix release. XRG-ng 0.2.1 on macOS could use a full CPU core continuously;
0.2.2 brings that back to a few percent of one core. It also makes AI token
accounting cheaper and more accurate on both platforms.

## macOS

- **Much lower CPU use.** Two causes kept 0.2.1 busy, measured on a real
  machine at about 90–110% of one core:
  - The Temperature graph re-sorted every sensor once per sensor reading.
    With a few hundred SMC and HID sensors that was seconds of main-thread
    work every five seconds. Sensors are now sorted once per update.
  - One AI log over the parser's size limit made every AI scan discard its
    work and start again five seconds later. A scan now keeps each file's
    result even when another file fails, and retries an unchanged failing
    file at most once a minute. Failed scans still report as failed and keep
    the last complete totals.

  With the same sensors, settings and logs, 0.2.2 measured 3.1% of one core,
  against 89.3% for 0.2.1.
- **Growing AI logs are read incrementally.** A Claude Code or Codex session
  log that grows is no longer parsed again from the start on every change.
  XRG-ng continues from where it stopped, after checking a SHA-256 of every
  earlier byte. Any edit, truncation or replacement of the earlier content
  makes it parse the whole file again, so totals always match a full read.
  Gemini session files are still read whole.
- **AI log scanner.** A log file rewritten to the same size is now re-read,
  so token totals, model attribution and continuity follow the new content.
  Previously the scanner compared only the modification date, size, inode and
  device, so a rewrite that kept or restored the modification date, or one
  that landed within the same timestamp tick, could go unnoticed. The scanner
  now also compares the change time (ctime), which writers cannot set back,
  and trusts unchanged metadata only for a snapshot taken more than 3 seconds
  after the file's last modification or change time. A recently written file
  is therefore read again on the next scan, and an unchanged file is not
  re-read after that.

## Linux

- **AI log scanner.** A log file rewritten to the same size within the
  filesystem's timestamp granularity is now re-read, so token totals, model
  attribution and continuity follow the new content. Previously such a
  rewrite could go unnoticed on filesystems with coarse timestamps (observed
  on Raspberry Pi 5, in 4 ms steps). The scanner still trusts unchanged
  metadata, but only for a snapshot taken more than 3 seconds after the
  file's last modification or change time. A recently written file is
  therefore read again on the next poll, and an unchanged file is not
  re-read after that.

## Both platforms

- **Larger AI logs count.** The per-file limit for AI usage logs rises from
  64 MiB to 1 GiB; single records stay limited to 8 MiB. Long Claude Code or
  Codex sessions over 64 MiB previously left that provider's totals marked as
  failed. A large file is read in full once, then only its new records.

## Installing

macOS 26 or newer, universal (Apple silicon and Intel):

- Homebrew: `brew install --cask sdelavega/tap/xrg-ng`
- Existing installs offer the update through **Check for Updates…**.
- Or download the DMG and drag XRG-ng into Applications; the ZIP extracts to a
  portable copy. SHA-256 checksums accompany the downloads.

Linux, x86-64 and ARM64: each architecture ships a `.deb`, `.rpm`,
`.pkg.tar.zst`, `.AppImage` and a relocatable `.tar.gz`, with the Swift
runtime bundled so no toolchain is needed to run them. glibc 2.39+ is
required; Alpine/musl is not supported. See the
[Linux installation guide](https://github.com/sdelavega/XRG-ng/blob/main/xrg-linux/preview/README.md)
for dependencies, installation and removal, and verify downloads with the
[release signing instructions](https://github.com/sdelavega/XRG-ng/blob/main/signing/README.md)
and the release signing fingerprint:

```text
8DAC471BBD9BC89CD1C881AEA09F0F040FA937A4
```

## Validation and limits

- **macOS**: the full Release suite runs natively on ARM and under Rosetta
  x86_64, plus packaged launch/restore/shutdown checks. The CPU figures above
  come from running 0.2.1 and 0.2.2 side by side as isolated copies with the
  same preferences, sensors and logs, after a two-minute warm-up. Rosetta
  validation does not replace physical Intel hardware testing.
- **Linux**: the full debug gate runs in an ARM64 container. Release CI
  results for this version are added before publication.
- **Windows**: no Windows build ships; compile and unit-test checks run in CI.

### Known limitations

- On Linux and Windows builds of the shared Swift core, which have no
  CryptoKit, appended logs are always parsed from the start. The Linux app
  is unaffected: its own scanner already resumes appended logs.

The macOS update feed and the Homebrew cask follow the unified build number.
Feedback, working setups and bug reports are welcome and encouraged.
