# XRG-ng 0.2.1

XRG-ng 0.2.1 aligns every platform on one version and build number, brings
automatic updates to the macOS app, and ships the monitoring work developed
since the macOS 0.1.0 and Linux 0.2.0 releases. macOS and Linux now carry the
same version 0.2.1 (build 2), verified by a cross-platform version check.

## macOS

Changes since 0.1.0, grouped by what you see:

- **New graphs.** An Apple Neural Engine panel on Apple silicon (enabled by
  default there, hidden on Intel) shows active-time percentage where macOS
  exposes it, power in watts, and observed fabric traffic. Optional **VRAM**
  and **Fans** graphs (both off by default) plot up to three sources each,
  with persistent source selection.
- **New monitoring details.** The CPU and Memory graphs open a searchable
  process table with live, instance-bound inspector windows and confirmed
  Terminate/Force Kill/Pause/Resume actions. CPU and GPU graphs keep persistent
  source selections, and the GPU menu adds a utilization-only view. Network
  and Disk graphs show observed session transfers with separate reset actions.
- **Presentation.** Preferences → Graphs reorders modules, toggles visibility,
  and sets per-graph heights, colors, curve fills and display effects. The
  Classic theme now matches the original XRG palette and is the default.
  Themes load and save portable JSON palettes that interoperate with the Linux
  app; existing XTF files keep working.
- **History controls.** Every graph has an explicit retained-sample capacity,
  and CPU, Memory, Network, Disk, GPU, NPU, VRAM, Fans, Temperature and
  Battery each offer a 1–60 minute observation time window; AI offers 1–1,440
  minutes. System sampling targets span 200 ms–10 s. Gaps and failures stay
  visible instead of being bridged with stale values.
- **Sampling reliability.** Core system histories keep collecting while their
  graphs are hidden, timers keep firing during AppKit menu tracking, battery
  polling is gated on elapsed continuous time, GPU snapshots collect on a
  coalesced serial worker, and wake invalidates in-flight GPU work and
  rebases I/O rates rather than drawing wake spikes.
- **AI token monitoring.** Observed session/daily accounting with per-model
  attribution for recorded models, daily token budgets with native
  notifications, a nominal five-second collection cadence independent of graph
  refresh, and collection that continues while the AI graph is hidden.
- **Weather.** 6/12/24-hour history windows with optional secondary curves.
- **Sensors.** The SMC backend is now first-party GPL code making read-only
  requests with strict numeric formats and generated labels; relative-to-limit
  channels are no longer presented as absolute temperatures. This replaces the
  former APSL-derived sensor implementation in the app.

New in 0.2.1 itself:

- **Updates.** Sparkle 2.10.1 adds **Check for Updates…** to the application
  menu, reading a signed update feed; once you allow automatic checks, they
  run daily. Existing 0.1.0 settings are preserved, and Sparkle asks you
  about automatic checks itself.
- **Homebrew.** The app is installable as a cask:
  `brew install --cask sdelavega/tap/xrg-ng`.
- **Support.** **Help → Support XRG-ng…** opens the project's GitHub Sponsors
  page.

## Linux

Changes since linux-v0.2.0:

- **Dashboard.** Ctrl+M or a hostname double-click collapses the dashboard to
  a strip, with optional transient hover expansion in General preferences;
  explicit expansion pins the window open and sampling continues while
  collapsed.
- **History and transfers.** Graph menus offer **Clear graph history**, the
  application menu offers **Clear all graph histories**, and Network/Disk show
  observed session transfers with a separate **Reset session transfers**;
  plots, rates and totals stay independent.
- **AI.** Observed session/daily counters and token budgets in
  Preferences → AI, with optional desktop alerts over D-Bus, per-model
  attribution, retained-sample capacities and a 1–1,440-minute observation
  window. Collection continues while hidden when tracking is enabled.
- **Sensors.** **Sensors and statistics…** shows current/minimum/average/
  maximum readings for every readable input plus a copyable diagnostic report.
- **Battery and weather.** An optional signed-power battery history, and
  weather history windows with secondary curves and independent units.
- **Capacities and windows.** Every graph has an explicit retained-sample
  capacity; CPU, Memory, Network, Disk, GPU, NPU, VRAM, Fans, Temperature and
  Battery add 1–60-minute observation windows; sampling targets span
  200 ms–10 s.
- **Hardware.** The NPU collector recognizes the Rockchip vendor driver alias
  on RK3588 systems.
- **About.** The About window links to GitHub Sponsors.

The release CI (`linux.yml`) is configured to build the frozen 0.2.0
application and test a real 0.2.0 → 0.2.1 archive upgrade with custom
preferences, in addition to native package revision upgrades; it passes on
x86-64 and ARM64 (see Validation and limits).

## Windows

There is no Windows release in 0.2.1. The shared Swift core and the Rust
collector crate now compile and pass their unit tests on Windows targets —
verified manually on a Windows 11 machine — which is groundwork for the
planned port; the `windows.yml` workflow runs the same checks in CI.
See the
[Windows port plan](https://github.com/sdelavega/XRG-ng/blob/main/docs/WINDOWS_PORT.md)
for what already builds and what each collector still needs.

## Installing

macOS 26 or newer, universal (Apple silicon and Intel):

- Homebrew: `brew install --cask sdelavega/tap/xrg-ng`
- Or download the DMG and drag XRG-ng into Applications; the ZIP extracts to a
  portable copy. SHA-256 checksums accompany the downloads.

Linux, x86-64 and ARM64: each architecture ships a `.deb`, `.rpm`,
`.pkg.tar.zst`, `.AppImage` and a relocatable `.tar.gz`, with the Swift
runtime bundled so no toolchain is needed to run them. glibc 2.39+ is
required; Alpine/musl is not supported. See the
[Linux installation guide](https://github.com/sdelavega/XRG-ng/blob/main/xrg-linux/preview/README.md)
for dependencies, installation and removal, and verify downloads with the
[release signing instructions](https://github.com/sdelavega/XRG-ng/blob/main/signing/README.md)
and the release signing fingerprint:

```text
8DAC471BBD9BC89CD1C881AEA09F0F040FA937A4
```

## Validation and limits

- **macOS**: the full suite runs natively on ARM and under Rosetta x86_64 for
  Release builds, plus packaged launch/restore/shutdown checks. Rosetta
  validation does not replace physical Intel hardware testing. Sleep/wake
  handling is covered by synthetic events, not physical tests. Sensor accuracy
  and a complete VoiceOver session remain separate validation work.
- **Linux x86-64**: release validation runs in CI (`linux.yml`) and passes:
  Debug and Release builds, X11 and nested Wayland desktop checks, clean
  install/launch/upgrade/remove checks on Ubuntu, Fedora and Arch Linux, and
  the 0.2.0 → 0.2.1 archive upgrade test, on both x86-64 and ARM64 runners.
- **Linux ARM64**: the full release gate runs in an ARM64 container. On
  physical hardware, Raspberry Pi 5 (Debian 13) and Orange Pi 5 Plus (RK3588)
  each pass the complete debug gate for this release — live collection, the
  headless/UI smokes and every managed X11/Wayland desktop and collapse check.
  (Three AI log-scan unit tests originally assumed sub-4 ms file-timestamp
  changes the Pi's kernel cannot represent; their fixtures now pin distinct
  metadata, with no scanner change.) Hardware support remains a best-effort
  attempt: most GPU/NPU and sensor combinations have not been physically
  tested, and NPU compute workloads remain unverified on the Pi.
- **Windows**: compile and unit-test checks run manually on a Windows 11
  machine and pass in CI (`windows.yml`).
  No Windows build ships.

### Known limitations

- If an AI log file is rewritten to the same size within the filesystem's
  timestamp granularity after XRG-ng has read it, the change can go unnoticed
  and token totals, model attribution and continuity stay stale until the
  file changes again. The scanner compares file metadata (device, inode, size,
  mtime, ctime), not content hashes, by design; this behaviour predates
  0.2.1. It is most likely on filesystems whose kernels advance file
  timestamps in coarse steps (observed on Raspberry Pi 5, in 4 ms steps). A
  fix is planned after 0.2.1.

The macOS update feed and the Homebrew cask follow the unified build number.
Feedback, working setups and bug reports are welcome and encouraged.
