# XRG-ng 0.2.3

A settings release. macOS and Linux now share the same settings window, backed
by one settings catalog and one settings document, drawn with the Aether7b
design language. Opening 0.2.3 for the first time migrates your 0.2.2 settings
once and leaves the old settings in place, so you can still go back to 0.2.2.
Linux gains a Stocks graph, and the sensor-naming work lands on macOS.

## Both platforms

- **One settings window.** The old preferences windows are replaced by a single,
  catalog-driven window with the same sections on both platforms: **General,
  Appearance, Graphs, Sources, AI, Weather, Stocks, Themes & import**. One
  catalog is the source of truth for every setting's label, range and default,
  and both windows build their controls from it. The window uses the
  Aether7b design language only — its colours, type, spacing, radii, focus ring and motion come from
  generated tokens — follows the system light/dark appearance, honours reduced
  motion, and labels every control for assistive technology. Changes apply and
  save instantly; there is no draft and no Apply button.
- **One settings file.** Both platforms read and write the same JSON document.
  It lives at `~/Library/Application Support/XRG-ng/settings.json` on macOS and
  `$XDG_CONFIG_HOME/xrg-ng/settings.json` (`~/.config` by default) on Linux.
  Writes are atomic; keys this version does not know are preserved, so a
  document from the other platform or a newer one survives a save; a value that
  fails validation falls back to that key's default and is reported, and a file
  that cannot be read is never overwritten without your explicit confirmation.
- **Upgrade and downgrade.** On first launch, when there is no settings
  document yet, 0.2.3 migrates your 0.2.2 settings once — from the macOS
  `NSUserDefaults` domain, or by upgrading the Linux version-40 `settings.conf`
  in memory and converting it — and writes the document. Every old setting is
  left untouched, so reinstalling 0.2.2 still reads its own preferences and
  downgrading works. After that, the document is the only source of truth and
  0.2.3 never writes the old locations.
- **0.2.2 text preferences.** Some 0.2.2 on/off preferences were stored as text
  (for example `YES` and `NO`). Migration reads them the way 0.2.2 read them,
  so a stored `YES` or `NO` becomes the same value it did in 0.2.2 instead of
  being rejected as an invalid value.

## macOS

- **Temperature sensors have real names.** Apple Silicon temperature readings
  are no longer shown only as raw SMC keys. XRG-ng now picks one best name per
  sensor from the evidence it has: names verified against the machine's own
  SMC firmware (die, PMU, storage, Neural Engine and ambient-light channels),
  Apple's board descriptions, and credited community references — Stats by
  Serhiy Mytrovtsiy (MIT) and the Asahi Linux device trees (GPL-2.0+ OR MIT).
  A model table covering every Mac that runs macOS 26 or later, Intel and
  Apple Silicon, selects the right names for the host. Saved graph choices
  keep their raw keys, so existing setups are unaffected — except selections
  saved against duplicate-product HID sensors: an old key such as
  `gas gauge battery` no longer reliably identifies a physical source, so it
  becomes unavailable and must be reselected from the now-distinct channels.
  It is not silently redirected, and sensor histories and settings are not
  reassigned.
- **The Temperature settings group sensors.** The sensor pickers now separate
  **Identified**, **Unidentified** and **Suspected Unused** sensors. A sensor is
  suspected unused when the firmware reports no producer for it, or when an
  unidentified reading has not changed for 60 updates (at least five minutes).
- **Missing readings no longer look like zero.** A sensor that is present but
  has no current reading is recorded as a gap in the graph history instead of
  0 °C, so a briefly missing sensor can no longer drag the thermal scale down
  to the freezing point. Copied diagnostics report unavailable readings as
  `n/a` rather than a value, and failed battery polls keep their history gaps
  instead of counting as 0%.
- **More sensors stay visible and distinct.** Distinct HID temperature channels
  that share a product name are kept as separate channels, discovered HID
  channels stay in the normal sensor picker, and legacy Intel sensor
  descriptions use the exact hardware branch instead of a broad family name.
  The sensor window's initial width now fits the friendly names.
- **Battery readings are more reliable.** Nested battery capacity readings are
  read correctly, desktops that explicitly report no battery no longer show
  one, and both battery histories are reset when the installed battery count
  changes, so a swapped or newly detected battery does not inherit stale
  history.
- **The NPU graph survives sleep.** Neural Engine telemetry is invalidated
  across sleep, wake and shutdown, so the graph no longer shows stale
  readings captured before the machine slept.
- **Credits.** The About box and THIRD_PARTY_NOTICES.md now record the Stats
  and Asahi Linux sources for sensor names, and the Asahi Linux documentation
  (CC BY 3.0) for Mac model data.

## Linux

- **A Stocks graph.** Linux can now show the same Stocks graph as macOS: the
  same ticker list and limits, a one-year daily history and a 15-minute
  intraday quote from the same Yahoo chart data, parsed by the shared core,
  with the same refresh cadence and failure handling. It is **off by default**
  (turn it on in **Graphs → Stock graph → Visible**). Stocks settings are ordinary
  shared catalog entries.
- **Preferences.** The old platform-local preferences window and file give way
  to the shared settings window and document described above; the first 0.2.3
  launch migrates a 0.2.2 `settings.conf` once and leaves it byte-for-byte
  untouched for downgrade.

## Installing

macOS 26 or newer, universal (Apple silicon and Intel):

- Homebrew: `brew install --cask sdelavega/tap/xrg-ng`
- Existing installs offer the update through **Check for Updates…**.
- Or download the DMG and drag XRG-ng into Applications; the ZIP extracts to a
  portable copy. SHA-256 checksums accompany the downloads.

Linux, x86-64 and ARM64: each architecture ships a `.deb`, `.rpm`,
`.pkg.tar.zst`, `.AppImage` and a relocatable `.tar.gz`, with the Swift
runtime bundled so no toolchain is needed to run them. glibc 2.39+ is
required; Alpine/musl is not supported. See the
[Linux installation guide](https://github.com/sdelavega/XRG-ng/blob/main/xrg-linux/preview/README.md)
for dependencies, installation and removal, and verify downloads with the
[release signing instructions](https://github.com/sdelavega/XRG-ng/blob/main/signing/README.md)
and the release signing fingerprint:

## Validation and limits

- **macOS**: the full Release suite (`Tools/ci-macos.sh Release`) runs natively
  on arm64 and under Rosetta x86_64, with the universal-build metadata and
  runtime-class checks and packaged launch/restore/shutdown checks; it passes
  on both architectures. The 0.2.2 → 0.2.3 → 0.2.2 upgrade/downgrade check
  (`Tools/settings-upgrade-macos.py`) passes on three seeds — the default
  fixture, a vertical-orientation seed and a preferred-height seed — checking
  the migrated document, empty migration diagnostics, validated graph sizes
  and byte-identical 0.2.2 defaults after downgrade. A one-time local run of
  that check against a real 0.2.2 user's preferences export also passed; the
  export was deleted afterwards and the real preferences were left untouched.
- **Linux**: the full gate (`Tools/ci-linux.sh`) runs in the ARM64 validation
  container — Swift shared-core tests, the C ABI smoke, Rust formatting,
  clippy and tests, non-root permission tests, headless and X11/nested-Wayland
  desktop checks, and the file-picker, history and collapse smokes — and
  passes. The 0.2.2 → 0.2.3 → 0.2.2 upgrade check
  (`Tools/application-upgrade-linux.py`) also runs in that container and
  passes, asserting the migrated `settings.json` matches the expected
  document, `settings.conf` is byte-identical, and 0.2.2 still reads its own,
  unchanged effective preferences after the upgrade.
- **CI has not run for the final 0.2.3 build 4 revision.** The workflow steps
  that run these checks are wired and reviewed; the results above are local
  validation, and release validation in CI on macOS, Windows and both Linux
  architectures is still to come.
- **Windows**: no Windows build ships; the shared core is still expected to
  build and pass its unit tests there, but that has not been run for this
  version.

### Known limitations

- **Linux Stocks comes from the shared core.** On Linux, the Stocks graph's
  presentation (visibility, style, height and colours) and its position in the
  graph order now come from the shared settings core — the single model shared
  with macOS — rather than a Linux-local override. The shared document is
  authoritative; the old Linux settings file is read only once, at migration,
  and no longer drives them.
- **Linux Stocks fetches tickers sequentially.** The Linux Stocks collector
  requests tickers one at a time within a refresh cycle (each request bounded
  by the weather timeout, and all of it off the sampling thread), whereas
  macOS requests them concurrently. With a long ticker list a full refresh
  cycle can therefore take longer on Linux, on the same two-hour cadence.
- **macOS: an editor that ignores the settings lock can still race the final
  instant.** Every write to the shared `settings.json` — including the
  first-launch migration — runs as one locked transaction over
  `settings.json.lock` (read, compare, stage, re-check, replace), so two
  copies of the app, or the app and its own helpers, never lose each other's
  edits. The file's identity is re-checked immediately before the atomic
  replace, but an external editor that ignores the advisory lock can still
  write in the final instant between that re-check and the rename; such an
  editor's change can be lost.
- **Reduced motion on Linux.** The Linux settings window follows GNOME's
  reduced-motion preference and an explicit override; other desktops'
  reduced-motion signals are not exposed by the UI toolkit, so transitions
  remain animated there.
